# I18N — Korean, Japanese, Traditional and Simplified Chinese

Plan of record for localising Maple Symbols. Read it before adding a user-facing string, before touching `src/lib/routes.ts`, and before any work on the language selector. Rules are numbered so a review can cite them (`I18N-4`). §0 is the decision that gates everything, §3 the audit of what the code blocks today, §7 the rollout order.

What exists is groundwork, not a translation. On `v2`, `useLocale()` follows the URL's edition (`src/lib/routes.ts` `servedLocale`): an edition gets its language as soon as that language is in `CATALOGUE_LANGUAGES`, which `LOCALES` in `src/i18n/index.ts` now reads. `DEFAULT_LOCALE` in `src/lib/routes.ts` is the one place the language is named: it fills `<html lang>`, `og:locale` and the JSON-LD `inLanguage`, and a test holds the manifest's `lang` to it. `src/lib/format.ts` formats every number, plural and display date through that locale. B-1, B-2, B-4, B-5, B-7 and B-9 are closed. Every interface string lives in the English catalogue in `src/i18n/en/` (one file per area); components read it with `useMessages()` and render sentences with accent markup through `<Message>`; symbol and quest names go through `symbolNames()` in `src/i18n/gameNames.ts`; game terms (Sacred Symbol, Arcane Power, Catalyst…) are placeholders filled per edition from `src/i18n/terms.ts` (§10). What does not exist yet: a second locale, locale-prefixed URLs and `hreflang` (I18N-4), and a working language selector (B-8, still a disabled "Coming Soon" tooltip).

## 0. The scope question (decided 2026-09-22: regional game data; see `docs/REGIONS.md`)

**Are we translating the interface, or shipping the regional game?** The four target languages map to MapleStory versions that are not the same game as GMS:

- KMS, JMS, TMS and CMS are on different content schedules. Symbols that exist in GMS may be absent, and symbols that exist there may be missing here.
- Daily and weekly quest yields, meso costs and level caps have differed between versions historically.
- Region names have official localised names; a machine translation of "Vanishing Journey" is wrong, not just clumsy.

Two coherent products come out of that:

| Option                 | What it means                                                                                                                        | Cost                                                                                                |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------- |
| **Interface only**     | The numbers stay GMS. A Korean-reading GMS player gets a Korean UI. Symbol names use the official Korean names for the same regions. | ~110 UI strings + 32 game names per language, no data model change.                                 |
| **Regional game data** | Each locale gets its own symbol table, quest yields and caps, so a KMS player gets KMS answers.                                      | A `version` dimension through `symbols.json`, the store, the persistence key and every calculation. |

They are not the same project, and the second changes the data model, so it belongs in the 2.0 conversation (`docs/V2_PLAN.md`). **Superseded 2026-09-22 (Brian): full regional data for all six servers, all launching together; the design is `docs/REGIONS.md`, which also replaces locales with editions (region + language) in the URL rules below.** What follows is the earlier decision, kept for the record. **Decided 2026-09-16 (Brian): interface only.** The numbers stay GMS; the interface, symbol names and quest names are translated, the names from each region's official client (I18N-6). Regional game data is out of scope; revisit only if a region's players ask for their own server's numbers, which would add a region dimension to `symbols.json` and every calculation.

## 1. Locales and URLs

- **I18N-1 Five locales, BCP-47 tags: `en` (default), `ko`, `ja`, `zh-Hant`, `zh-Hans`.** Use the script subtags, not `zh-TW`/`zh-CN`: script is what actually differs, and `hreflang` accepts them. Set the tag on `<html lang>`, in `inLanguage` in the JSON-LD, and in the manifest.
- **I18N-2 Locale lives in the URL path: `/ko/handbook`, `/ja/`, `/zh-Hant/changelog`.** _(Superseded on 2026-09-22: the prefix is the server's code, `/kms/handbook`, and names an edition, which carries its language; `docs/REGIONS.md` D-3.)_ English stays at the bare path with no `/en/` prefix. A client-side toggle on one URL is invisible to search engines (SEO-24), and a cookie or `Accept-Language` redirect hides the other languages from crawlers entirely.
- **I18N-3 Every page links to every other language with `hreflang`, plus `x-default` pointing at the English URL.** Reciprocal and absolute. Generated from `ROUTES` × locales, like the sitemap, and listed in `sitemap.xml` so all twenty URLs are discoverable.
- **I18N-4 `routes.ts` stays the single source.** `RoutePath` keeps describing the unlocalised path; a `Locale` type multiplies it. `urlFor(path, locale)`, `routeFor(pathname)` strips a known locale prefix first, and titles and descriptions move from literals into the per-locale message catalogue. The routes plugin then emits the localised `pageMap`, the `hreflang` block and the full sitemap.
- **I18N-5 The language a visitor picks is remembered, never used to redirect.** Store the choice (localStorage is fine here; it is a per-viewer convenience) and use it to pick the link target on the switcher. Do not auto-redirect on `Accept-Language`: it breaks shared links, back buttons, and crawling.

## 4. Library choice (decided: typed dictionary, no dependency)

| Option                                        | Fit                                                                                                                                                                                                                                                                                                 |
| --------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Typed dictionary + `Intl`** (no dependency) | ~110 strings is small. A `Record<Locale, Messages>` with a `const` English catalogue as the key type gives compile-time checking of every key in every language, and `Intl.PluralRules`/`NumberFormat` cover the rest. Markup placeholders (B-1) need a small `<Message>` helper, perhaps 30 lines. |
| **react-i18next**                             | The default answer, plural and interpolation handling included, `<Trans>` solves B-1 out of the box, and translators get a familiar JSON format. Costs a dependency and a provider, and its key typing needs setup to match what the hand-rolled version gets free.                                 |
| **Lingui**                                    | Compiles messages at build time, so the runtime is smaller and unused strings are caught. Costs a Babel/SWC step in a Vite build that currently has none.                                                                                                                                           |

**Decided 2026-09-16 (Brian): the typed dictionary.** The English catalogue is a `const` object and its type is the contract, so a missing key in any language fails `pnpm typecheck`. Plurals and numbers go through `src/lib/format.ts`. Markup inside a sentence (B-1) uses a small in-repo helper that splits a message on named placeholders and renders the matching element, so translators see one whole sentence per key. The other two options are recorded above for the reasoning; do not add either without reopening the decision.

## 5. Rules for new work, starting now

- **I18N-10 A new user-facing string is one whole sentence, not fragments.** Write it as one catalogue message with the accent markup inside (`<b>…</b>`, rendered by `<Message>`), never as JSX fragments around a `<span>` (B-1, closed; `src/i18n/catalogue.test.ts` enforces the markup).
- **I18N-11 No hard line breaks inside copy.** Use layout (width, flex) to wrap (B-2).
- **I18N-12 Format numbers and dates through the app locale**, never through the browser default (B-4, B-5). A meso amount inside a sentence goes through `formatMesos` (the reader's own units: 39억 3,010만, 39億3010万); a table column stays on `formatNumber`'s full digits (`docs/REGIONS.md` D-11). A completion or attainment day goes through `formatDay`: English keeps ISO `2027-01-28`, Korean, Japanese and Chinese get their own form with the weekday (`2027. 1. 28. (목)`, `2027/1/28(木)`), Brian's choice on 2026-09-23; graph ticks and `<time dateTime>` stay ISO.
- **I18N-13 New layouts survive a string twice as long as the English one.** Check the longest target string, not the English one, against the fixed widths in DESIGN_SYSTEM §5 (B-6).
- **I18N-14 Plurals go through `Intl.PluralRules`**, never `n > 1` (B-9).
- **Game terms are placeholders** (`{sacredSymbol}`, `{arcanePower}`), filled per edition: I18N-15 to I18N-18 in §10.

## 6. Testing

- Every locale has every key: `Catalogue<typeof en>` makes a missing key a type error, and `src/i18n/catalogue.test.ts` also checks key order, placeholders, empty strings and markup per locale.
- No untranslated literal: extend the source scan in `src/test/seo.test.tsx` to flag new English literals in JSX outside the catalogue once extraction is done.
- Render smoke per locale: mount each route under each locale and assert no crash and a non-empty `h1`. The per-route SEO test already does this for English; multiply it by locale.
- Metadata: `hreflang` reciprocity (every page lists every locale, every target resolves), and the sitemap contains all locale URLs.
- Longest-string layout: a viewport test at 360 px with the longest catalogue entry, not the English one.

## 10. Game terms and name sets

A **name set** is one client's official vocabulary (REGIONS §2): `en-gms`, `en-msea`, `ko`, `ja`, `zh-Hant`, `zh-Hans` (`NAME_SETS` in `src/i18n/terms.ts`). Each edition names its own (`nameSet` in `EDITIONS`, `src/lib/routes.ts`). GMS and MSEA share the English catalogue but not their words: GMS says "Sacred Symbol" and "Arcane Power", MSEA "Authentic Symbol" and "Arcane Force" (D-19).

- **I18N-15 A game term in copy is a term placeholder, never a literal.** `"{pageGame} {arcane} & {sacredSymbol} Calculator | Maple Symbols"`. `TERMS[nameSet]` in `src/i18n/terms.ts` holds the words; each placeholder is one form, so English reads without string surgery: `{sacredSymbol}`, the plural `{sacredSymbols}`, `{aSacredSymbol}` with its article ("a Sacred Symbol", "an Authentic Symbol"), `{sacredPower}`, `{sacredCatalyst}`, `{sacredSelector}`, `{regularServer}`, `{demonAvenger}`, `{xenon}` and their arcane twins. `{pageServer}` is the page's own server ("GMS", "MSEA") and `{pageGame}` the game as the calculator title names it ("MapleStory" on GMS, the server code elsewhere, so MSEA's title fits SEO-6; Brian, 2026-09-23), both from the edition rather than the name set (`pageValuesFor` in `routes.ts`). A term is a word the client names; a word that changes only with the language (mesos, level, EXP) stays in each catalogue.
- **I18N-16 The effective name set.** A page uses its edition's name set only when it is served in that edition's language (`nameSetFor(edition)`: `servedLocale(edition) === edition.language`); otherwise GMS English. So an untranslated KMS page (English today) reads "Sacred Symbol", never an English sentence with Korean words in it.
- **I18N-17 Terms are filled before components see the catalogue.** `useMessages()` returns `messagesFor(locale, nameSet, pageValuesFor(edition))`, the catalogue with every term replaced, memoised per page; `editionMessages(edition)` is the same for callers that know an edition. Page titles and descriptions go through the same fill in `routes.ts` (`pageMetaFor(path, edition)`, read by `pageMap` and `applyToIndexHtml`, and so by the routes plugin, and by `App.tsx` and `SEO.tsx`), so each edition's head carries its own words. Run-time placeholders (`{count}`, `{server}`…) are left for `interpolate()` and `<Message>`; term names are reserved, and `src/i18n/terms.test.ts` fails if any term placeholder survives in any edition's catalogue or a run-time one is lost.
- **I18N-18 Term values only from the client or official patch notes (D-12).** A value not yet seen there carries an `UNCONFIRMED` comment next to it. Symbol and quest names are not terms; they are `GAME_NAMES` (§9), keyed by the same name sets.

**Adding a term:** add the field to `Terms` with a one-line comment, give it a value in every table (typecheck lists the ones missing), write the placeholder into the English copy, and run `pnpm exec vitest run terms`: a term no message uses fails as dead weight. **Adding a name set's table** (with its catalogue): add `TERMS[<set>]` with every term and its source in a comment; `termsFor` throws for a set without one, and the prerender renders every edition, so a translated edition cannot build without its table.

The MSEA table's source is maplesea.com's v251 and v252 patch notes ("Authentic Symbol", "Authentic Force", "Arcane Force", "Authentic Catalyst"). Still UNCONFIRMED there, GMS wording or built from a confirmed term until an MSEA screenshot or patch note settles them: the "Arcane" and "Authentic" toggle labels on their own, "Arcane Symbol(s)", "Arcane Catalyst", "Symbol Selector", "Arcane Symbol Selector", "Authentic Symbol Selector", "Regular Server", "Demon Avenger" and "Xenon".
